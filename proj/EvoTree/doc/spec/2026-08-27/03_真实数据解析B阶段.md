## 一、真实动作格式（关键发现）

从真实 traj.jsonl 的 `prediction` 字段解析：

```
<tool_call>{"name":"computer_use","arguments":{"action":"click","coordinate":[1854,887]}}</tool_call>
<conclusion>Selected the folder to prepare for renaming.</conclusion>
```

- **工具名分两类**（决定 α 的 kind）：
  - `computer_use` → GUI 操作，`arguments.action` ∈ {click, key, type, terminate, ...}
  - `os.*` / `libreoffice.*` / ... → 真 MCP 工具
- **归堆键设计**：
  - GUI：`computer_use.<子动作>`（如 `computer_use.click`），**坐标丢弃**
  - MCP：`工具名 + 排序参数名槽位`，**参数值丢弃**
- **`<conclusion>`**：agent 自写的语义描述。**不用作归堆键**（每轮措辞不同，不稳定），
  仅可作可读注释。归堆用稳定的 `action` 子类型。
- **终止判定**：`is_terminal()` 识别 DONE / terminate，这类步不进经验统计。

## 二、真实数据闭环验收（demo）

用真实 rename 轨迹（click→key→type→click）学 3 遍后读小抄：

```
[经验] 推荐：
  computer_use.click —— 3次·成功率1.00·平均还差4步；完成后 computer_use.key 一步收尾
```

真实轨迹被正确清洗、建森林、读出带前瞻的推荐 —— **闭环在真实数据上工作**。

## 三、⚠️ 这个 demo 暴露的真实局限（重要洞察，非 bug）

小抄首推 `computer_use.click`、`平均还差 4 步` —— 反映的是**训练轨迹的质量问题**，
不是 EvoTree 的缺陷：

1. **这条轨迹的 agent 全用 GUI 点击**（4 步 click/key/type），**没用 MCP 工具**。
   而该任务本可一步 `os.rename_directory` 搞定（部署圣经的 MCP 模式就是如此）。
   → EvoTree 忠实学到了"这个弱 agent 的 GUI 打法"，而非最优路径。

2. **这恰恰印证 idea 的核心主张**：单条弱轨迹不够，必须"成败全记 + 多轨迹攒
   统计",让好路径（工具一步）与坏路径（GUI 四步）的 val 在数据积累中分出高下。
   当同时有 GUI 轨迹和 MCP 轨迹时，`os.rename_directory`（1 步·高成功率）的 val
   会碾压 `computer_use.click`（4 步），EvoTree 就会推荐工具 —— 这正是 TIR 提升
   的微观机制（idea §8）。

3. **对 M1 的启示**：pilot 需要的不是几条轨迹，是**同一任务的多条轨迹**（含工具
   和 GUI 两种打法），EvoTree 的价值才显现。这也是"地基②样本量"要验证的。
