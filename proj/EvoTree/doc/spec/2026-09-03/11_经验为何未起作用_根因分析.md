# V3 实验诊断：经验为何没起作用

> 日期：2026-09-06
> 数据：A800 `/data/songweishuai/projs/rh/EvoTree/runs/evotree_m2_20tasks_v3_20260903/`
> 结论先行：**记忆机制在运转，但喂给它的统计量是错的。** 有一个我在 P0 修复时
> 引入的子串匹配 bug，把每一次**成功**的 MCP 工具调用都记成了失败，导致
> `p(e)` 全面失真。在此之上还有三个独立的结构性问题。

---

## 0. 三个指标一起看，才看得出发生了什么

| 指标 | baseline | online | frozen | 方向 |
|---|---|---|---|---|
| **Acc**（均值） | 0.3158 | 0.4000 | 0.3000 | 持平/略降 |
| **TIR**（工具调用率） | 14.6% | 24.3% | **26.8%** | ⬆ 近翻倍 |
| **ACS**（平均步数） | 4.80 | 5.55 | **6.35** | ⬇ 恶化 32% |
| 声明 FAIL 的任务数 | 6/20 | 7/20 | **10/20** | ⬇ 更常放弃 |
| `[经验]` 注入率 | N/A | 0% | 79% | — |
| `[注意]` 注入率 | N/A | 98% | 100% | — |

**行为确实被改变了**：工具调用率从 14.6% 涨到 26.8%。所以不是"注入没生效"。
但同时步数变长、放弃率上升、准确率没动。

也就是说：**注入改变了模型行为，但改变的方向是"多调工具 + 多绕路 + 更早放弃"，
而不是"更准地调对工具"。** 原因在下面。

## 1. 根因：`is_error=False` 被判成了错误（P0 修复的回归）

### 1.1 Bug 位置

`evotree/distill_osworld.py` 的 `extract_error_note()`：

```python
_ERROR_MARKERS = ("error", "exception", "traceback", "failed")
...
lowered = execution_output.lower()
if any(marker in lowered for marker in _ERROR_MARKERS):
    return execution_output.strip()   # ← 判为失败
```

而 MCP 工具**成功**返回的原文是：

```
CallToolResult(content=[TextContent(type='text', text='1.0')], is_error=False)
                                                              ^^^^^^^^^ 含 "error"
```

`is_error=False` 里含 `error` 子串 → 命中 `_ERROR_MARKERS` → 返回非 None 的 note。

调用链：`osworld_integration.py` 的 `step()` 里
```python
note = _note_from_step(info, next_observation)
self.runtime.after_action(..., note=note, action_success=note is None)
```
`note` 非 None → `action_success=False` → 这条边记一次失败。

**每一次成功的工具调用都被记成了失败。**

实测确认：

| 输入 | 判定 | 应为 |
|---|---|---|
| `is_error=False` | FAIL | ok |
| `Traceback: OSError` | FAIL | FAIL ✓ |
| `{'result': 1.0}` | ok | ok ✓ |
| `error: no such file` | FAIL | FAIL ✓ |

### 1.2 后果一：工具边的 p 值全面失真

| | 边数 | 平均 p | p=0 的边 |
|---|---|---|---|
| **工具边** | 12 | **0.250** | **8/12** |
| **GUI 边** | 31 | **1.000** | 0/31 |

逐条工具边（全部来自 online 阶段的真实执行）：

```
os.copy_matching_files_with_hierarchy   n=2 n_succ=0 p=0.00   ← 污染
os.set_do_not_disturb                   n=1 n_succ=0 p=0.00   ← 污染
os.get_do_not_disturb_status            n=1 n_succ=0 p=0.00   ← 污染
os.set_default_terminal_size            n=1 n_succ=0 p=0.00   ← 污染
os.change_text_scale                    n=4 n_succ=0 p=0.00   ← 污染
os.get_text_scale                       n=3 n_succ=0 p=0.00   ← 污染
os.set_volume                           n=6 n_succ=0 p=0.00   ← 污染
os.get_volume                           n=1 n_succ=0 p=0.00   ← 污染
os.open_shell                           n=2 n_succ=1 p=0.50   ← 部分污染
os.open_shell                           n=2 n_succ=1 p=0.50   ← 部分污染
os.configure_auto_lock                  n=1 n_succ=1 p=1.00
os.open_shell                           n=1 n_succ=1 p=1.00
```

`os.set_volume` 调了 6 次、被记 6 次失败——但音量任务的 evaluator 是通过的，
说明工具本身是好的。

GUI 边则相反，全是 p=1.00（`computer_use.click` n=39 全成功）——因为 pyautogui
的返回里没有 `error` 字样，逃过了误判。

### 1.3 后果二：推荐栏被 GUI 动作垄断

`val = p · γ^d`，p=0 → val=0，永远排在最后。实际注入给模型的小抄：

```
[经验] 推荐：
  computer_use.wait —— 1次·成功率1.00·平均还差6步（低置信）；完成后 computer_use.click 一步收尾
  computer_use.double_click —— 1次·成功率1.00·平均还差7步（低置信）；完成后 computer_use.wait 一步收尾
```

**推荐栏里一个工具都没有。** 推荐"等待"和"双击"——这不是路径知识，是噪声。

⚠️ 但要注意：**TIR 仍然涨了**（14.6%→26.8%）。所以推动 TIR 上升的不是推荐栏，
很可能是下面的 `[注意]` 栏无意中充当了工具名录（见 1.4）。这一条我早前判断
错了，特此更正：不能说"系统在教模型别用工具"。

### 1.4 后果三：global_notes 100% 是污染

11 条笔记，**真正的错误 0 条**，全部是成功的工具返回值原文：

```
[os.set_default_terminal_size] CallToolResult(content=[TextContent(text='✅ Persisted de...
[os.set_volume]                CallToolResult(content=[TextContent(text='{"success":true...
[os.change_text_scale]         CallToolResult(content=[TextContent(text='1.0'...
[os.change_text_scale]         CallToolResult(content=[TextContent(text='1.5'...
[os.change_text_scale]         CallToolResult(content=[TextContent(text='2.0'...
[os.get_text_scale]            CallToolResult(content=[TextContent(text='1.5'...
[os.set_do_not_disturb]        CallToolResult(content=[TextContent(text='true'...
...
```

注意 `text='{"success":true'` —— 笔记内容本身就写着 success。

这些以 `[注意]` 注入 prompt，每条几百字符。副作用有两面：

- **坏的**：几千字符噪声挤占 prompt，且"注意"语义完全错位
- **可能是好的（意外）**：这些条目里含大量工具名（`os.set_volume`、
  `os.change_text_scale`…），无意中成了一份工具名录，**这大概是 TIR 上涨的
  真实原因**——模型看到有这些工具存在，就更倾向去调

即：**TIR 的提升来自噪声的副作用，不是来自学到的价值统计。**

## 2. 三个独立的结构性问题（与 bug 无关，各自都要修）

### 2.1 φ 状态签名退化：19/28 个节点是空签名

全部 28 个节点的签名分布：

```
x19  app='unknown'              window=''                      dialog=None   ← 68%
x5   app='Org.gnome.Nautilus'   window='user-virtual-machine'   dialog=None
x3   app='Gnome-control-center' window='user-virtual-machine'   dialog=None
x1   app='Gnome-terminal'       window='user-virtual-machine'   dialog=None
```

**68% 的节点是 `(unknown, '', None)`** ——观测里的 app/window 没被提取出来。
`osworld_adapter._fallback_observation()` 的注释早就写了这个前提：

> 这里不伪造真实 app/window：把轨迹元数据作为占位，方便格式测试；
> **接入真实 agent 时必须由 observation_factory 提供真实 φ 输入。**

在线路径走的是 `build_observation()`，它从 `osworld_obs["cur_app"]` /
`apps[cur_window_id]["title"]` 取值——但 OSWorld 在 `screenshot` 观测模式下
不提供这些字段，所以全部落到 `"unknown"` / `""`。

而且非空的那几个 window 全是 `user-virtual-machine`（主机名），**不是窗口标题**——
说明取到的字段本身也不对。

后果：
- 所有状态塌缩成同一个节点 → 树是扁平的，没有真实结构
- `to_success` 大量指向自己（`s0 → s0`），前瞻退化成"下一步还在同一个状态"
- 12/20 棵树只有 **1 个节点**

`dialog` 字段**全部为 None**——三元主键实际退化成二元，且其中一元是常量。

### 2.2 α 动作模板粒度过粗：所有点击是同一条边

```
x14  gui : computer_use.click       （聚合后 n=39）
x8   gui : computer_use.type        （聚合后 n=13）
x3   gui : computer_use.scroll
x2   gui : computer_use.right_click
x2   gui : computer_use.key
```

`distill_osworld.py` 用子动作类型归堆，坐标丢弃（符合文档），但**没有语义描述**。
后果是"点击屏幕任意位置"都归成一条边 `computer_use.click`，n=39、p=1.00。

推荐"click，成功率 1.00"对模型是零信息——它当然知道可以点击，问题是点哪里。

idea §4.1 要求的是"让 VLM 写一句语义描述（'点击 Format 菜单'）"，目前没实现。

### 2.3 样本量太薄：23/43 条边只有 n=1

```
n=1 : 23 条边   ← 53%
n=2 :  9 条边
n=3 :  3 条边
n=4 :  3 条边
n=5 :  2 条边
n=6 :  2 条边
n=7 :  1 条边
```

plan 里「地基②」的判断线是"关键边 n 能到 ~5–10 → MC 估计的 p 可信"。
现在超半数边 n=1，`p` 只能是 0 或 1，是纯噪声。小抄里那个"（低置信）"标注
正是这个的体现——`is_low_confidence` 阈值 `min_n=3`。

## 3. online 阶段 `[经验]` 注入率为 0%：设计层面的必然

online 的 111 步里，`[经验]` 出现 **0 次**。这不是 bug，是单轮设计的必然结果：

- τ 模板库对这 20 条真实指令产出 **20 个不同模板，零碰撞**（我早前验证过）
- online 从空记忆出发，做任务 k 时查 tree_k —— 空的，没有历史边
- 20 个任务全程没有任何一次模板复用

**所以 online 的 0.40 vs baseline 0.3158，在机制上不可能来自边级推荐。**
那 0.08 的差值只能来自 `[注意]`（98% 注入）或模型随机性。

要让 online 真正体现"边跑边学"，必须按 idea §12 让同一批任务重复曝光
（pass-1/2/3），第二轮起模板才会命中。

## 4. 轨迹实证

### 4.1 任务 4783cc41（base 0 / online 0 / frozen 1）

frozen 是唯一得分的一组，但看轨迹：

```
--- baseline: 3 步 ---
  step1  computer_use   pyautogui.write...
  step2  computer_use   pyautogui.write...
  step3  computer_use   DONE

--- online: 3 步 ---
  step1  computer_use   pyautogui.write...
  step2  computer_use   pyautogui.write...
  step3  computer_use   DONE

--- frozen: 8 步 ---
  step1-4  computer_use   pyautogui.write × 4
  step5-6  computer_use   pyautogui.click × 2
  step7    computer_use   pyautogui.write
  step8    computer_use   FAIL          ← 声明失败，但 evaluator 给了 1.0
```

frozen 多花了 5 步、最后**声明失败**，evaluator 却判 1.0（说明中途已把状态改对）。
这个 1.0 不能算作"经验起作用"的证据——它是"绕更多路、误判自己失败、但恰好
改对了状态"。

三组全程 **0 次工具调用**，全是 pyautogui。

### 4.2 全局：轨迹如何结束

| arm | DONE | FAIL | 撞 8 步上限 |
|---|---|---|---|
| baseline | 13 | 6 | 0 |
| online | 13 | 7 | 0 |
| frozen | **10** | **10** | 0 |

**frozen 声明 FAIL 的任务从 6 个涨到 10 个。** 注入让模型更常放弃。

没有任何一组撞到 8 步上限，所以步数增加不是被截断，是模型主动多走了。

## 5. 因果链总结

```
is_error=False 子串误判
  ↓
每次成功的工具调用记为边级失败
  ↓
工具边 p 平均 0.250（8/12 为 0），GUI 边 p 全 1.00
  ↓
val = p·γ^d → 工具边 val=0 → 推荐栏只剩 GUI 动作（wait/double_click）
global_notes 11/11 是成功返回值，真错误 0 条
  ↓
注入内容 = 无用的 GUI 推荐 + 几千字符的工具返回值噪声
  ↓
行为确实改变（TIR 14.6%→26.8%，因 [注意] 意外成了工具名录）
但方向错了（步数 +32%、FAIL +67%、Acc 持平）
```

叠加三个结构性问题（φ 退化 68%、α 粒度过粗、n≤1 占 53%），
**当前的经验树里几乎没有可用的决策信息。**

所以"经验没起作用"的准确表述是：**注入管道是通的，但管道里流的是噪声。**
这轮实验测的不是"EvoTree 有没有用"，而是"注入噪声会怎样"——答案是
让 agent 多调工具、多绕路、更早放弃。

## 6. 修复清单（按性价比排序）

### P0-1：修 `is_error` 误判（一行的事，影响最大）

`evotree/distill_osworld.py::extract_error_note`

当前用子串匹配 `"error" in lowered`。至少要做到：

1. 先排除 `is_error=False` / `"is_error": false` / `isError:false` 这类显式否定
2. 优先解析结构：MCP 返回带 `is_error=True` 时才判失败
3. 保留 `Traceback` / `Exception` 这类无歧义标记的子串匹配作兜底

修完必须重跑 online（重建记忆树），否则 frozen 用的还是污染数据。
建议加测试：`is_error=False` → ok，`is_error=True` → FAIL。

### P0-2：接通真实 φ（决定树有没有结构）

68% 节点是空签名。需要在 `build_observation()` 里从 **a11y tree** 真实提取
`(app, 归一化window, dialog)`，而不是依赖 OSWorld 在 screenshot 模式下不提供的
`cur_app`/`apps` 字段。当前拿到的 `user-virtual-machine` 是主机名，不是窗口标题。

这一条不修，树永远是扁平的，前瞻和汇合都不成立。

### P1-1：global_notes 只收真错误

修完 P0-1 后自动缓解，但还应加一层：note 入库前限长（当前几百字符原文直接进
prompt），并且只保留错误摘要而非完整 `CallToolResult` 原文。

### P1-2：val=0 的边不进推荐栏

即使修完 P0-1，仍会有真正 p=0 的边。当前 `retrieval` 无条件取 top-k，会把
"已知会崩"的动作推到首位。这是我早前列在待办里的 P1 项，仍未做。

### P2-1：α GUI 语义描述

`computer_use.click` n=39 p=1.00 是零信息推荐。需要 VLM 写语义描述
（idea §4.1 要求）。成本较高，但不做的话 GUI 侧的推荐永远无意义。

### P2-2：Setting I 三轮重复

online 单轮 + 模板零碰撞 = 边级推荐结构上不可能出现。必须按 idea §12
让同一批任务重复 3 轮。

### P2-3：换任务集

这 20 个任务是 0/1 终点检查型系统设置（音量/蓝牙/时区），且**三组轨迹里
几乎没有工具调用**（TIR 最高 26.8%）。EvoTree 的价值场景是多轮工具任务
（idea §4.3：前瞻专打"基准中 42% 的多轮工具任务"）。应选：

- 需要多步工具编排的任务
- 有中间状态、失败可恢复的任务
- 同类可复用模板的任务（τ 有碰撞，经验才能跨任务传递）

## 7. 这轮实验的净结论

**不能用这轮数据判断 EvoTree 的方法有效性。** 它测的是一个统计量被污染、
状态签名退化、样本量不足的系统。

**但它有三个确定的工程产出：**

1. 三组闭环全部跑通（baseline/online/frozen 各 20 任务）
2. 注入管道验证可用（frozen 79% 步命中 `[经验]`，100% 命中 `[注意]`）
3. frozen memory 只读完整性通过（22 文件 SHA-256 前后一致，CLEAN）

**以及一个用真实数据换来的诊断**：上面 6 节的修复清单，每一条都有实测数字支撑，
而不是代码审阅的推测。P0-1 和 P0-2 修完后重跑，才是第一次真正测方法。
