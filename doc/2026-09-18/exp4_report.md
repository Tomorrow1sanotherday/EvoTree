**第 1 步和第 3 步：警告就在 prompt 里，agent 照按不误。**

警告原文说的是"反复按也常打不开终端，要开终端优先用 `os.open_shell`"。整条轨迹里 `os.open_shell` 一次都没被调用。

### 4.2 这验证了第一性原理分析

exp2 之后的判断是：瓶颈在 **execution-grounding** 层，而经验注入作用在 **planning** 层。

exp4 是这个判断的直接检验 —— 把执行层知识以文字形式送到 planning 层，**无效**。

模型能读懂"别按这个键"，但它的动作生成不受这句话约束。尤其当屏幕没有可见变化、它判断"可能没按到，再试一次"的时候：文字警告是一句静态断言，而 agent 面对的是一个需要闭环反馈的操作问题。**给 planning 层喂知识，治不了 execution 层的病。**

**② 只在前 3 步（任务内）**：种子树的节点签名是 `('unknown','','')`。VM 刚起时窗口注册慢、`cur_app` 解析成 `unknown`，恰好匹配；第 4 步起窗口就绪、φ 变成真实 app，与种子节点不再匹配，推荐栏空 → 注意栏也断了。这就是 exp3 报告里的 **P1**，未修。

### 结论的强度

- **能说**：在 23393935 上，警告确实送达（3 次，原文可查），agent 行为未改变，分数未变。
- **不能说**：4127319a——按了 10 次的最典型病例——**一次警告都没收到**，它的行为不能用来支持任何结论。

所以严格讲，这是 **n=1 的证据**。但它是干净的 n=1：同一任务、同一种子、仅代码不同，修复前后可逐步对照。

## 七、下一步

文字警告这条路已经证伪（n=1，但干净）。三个方向，优先级从高到低：

### 7.1 改作用层：从"劝说"改成"改变可选项"

既然模型不听文字，就别用文字。注意栏现在是 advisory 文本，**可以改成对工具表本身的干预**：
- 把 `os.open_shell` 提到工具列表首位（`reorder_tool_list` 已有这个机制，但目前只按推荐分排序，没有接入注意栏的负面知识）
- 或者更强：对已知失败率极高的动作做**准入拦截**，像推荐栏拦薄硬币边那样

这才是真正作用在 execution 层的干预。

### 7.2 先修 P1，让注入连续

当前注入只在前 3 步。即便文字有效，3/12 的覆盖率也测不出效果。P1 不修，后续任何"注入类"实验都不可信。

### 7.3 换任务集

6 个任务里 3 个 baseline 就能做对（且 hotkey=0，压根不碰终端），另 3 个全败。**没有信号空间**：能改善的只有那 3 个失败任务，而它们的败因是同一个（终端打不开）。
