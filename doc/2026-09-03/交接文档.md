一句话：`write_episode` 原先把 `episode.success`（整轮成败）套到每一条边，导致

### 2.2 三个 arm 是什么（不是"跑三遍"）

`run_arm.py:18` `ARMS = ("baseline","frozen","online")`。20 任务各跑一次，跑三组，
差别只在记忆：

| arm | 记忆 | 回答 |
|---|---|---|
| baseline | 无 | 裸模型难度，用于给任务分难度桶 |
| online | 边跑边写（从空 memory 起） | 积累经验过程中有没有变好 |
| frozen | 只读 online 的最终 memory（关写入） | 攒好的记忆迁移到只读还有没有用 |

串行接力：baseline 独立脚本先跑 → online → frozen 复制 online 的
`memory/env-0` 并 `--no-evotree_write_enabled`。frozen 前后 memory SHA-256 必须
完全一致（证明只读没污染种子）。

> **这轮不能报"记忆净增益"**：idea §5 要求的"记忆禁用、同样重复 3 轮"对照基线
> 还没做（见待办 P2）。没有它，online 的提升分不清是记忆功劳还是任务重复曝光。
> 这轮的定位是"修复后能不能完整跑完 20 任务" + 给难度分桶提供数据。

## E. 为什么 CUA 快而我们慢（查证结论）

yuyang 的 CUA 69 题 20 分钟跑完，我们一个任务 21.9 分钟。查证后：

| | CUA | EvoTree OSWorld |
|---|---|---|
| 隔离 | podman **纯容器**（`cua-ppt-libreoffice`），原生 CPU | 容器里再跑 **QEMU 虚拟机** |
| CPU | 原生 | **TCG 纯软件模拟**（无 `/dev/kvm`） |
| 生命周期 | 8 个 worker **常驻复用**（Up 5 天） | **每任务重建**，引导+装依赖 5-6 分钟 |
| 并发 | **8 路并行** | 串行 `--num_envs 1` |

**不能简单切成 CUA 那种纯容器**：OSWorld 的 docker provider 本身就是"容器套 VM"
（`docker/manager.py:19` 下载 `Ubuntu.qcow2`），因为 benchmark 需要 `save_state` /
`revert_to_snapshot` 系统级快照，且任务会改系统设置（音量/时区/蓝牙）——容器做不到。
CUA 的 74 题都是 LibreOffice 文档操作，容器够用。

**KVM 也开不了**：`lsmod | grep kvm` 无输出，`/lib/modules/$(uname -r)/kernel/arch/x86/kvm/`
不存在，且我们在 k8s pod 里（`/proc/self/cgroup` 显示 `kubepods-pod...`）——
没法加载宿主内核模块。我早前说"找 songweishuai 挂个 /dev/kvm 就能快 10 倍"是**错的**。

**真正可行的提速**（按性价比）：
1. **并行 `--num_envs 4`** —— runner 原生支持（默认值就是 5），宿主 128 核、
   单 VM 只吃 4 核、内存 1007G 充足。**但有三个必须先解决的坑**：
   - 容器名写死：`provider.py:446` `name=os.getenv("EVO_CONTAINER_NAME","evo-osworld")`
     是全局变量，多 env 会撞名 → 必须改成带 `env_idx` 后缀
   - 端口竞态：`network_mode=host` + `_get_available_port()` 有 check-then-bind 竞态，
     v1 就是死在这（产物还叫 `INVALID-*-port-collision`）
   - 磁盘：`/data` 100% 满仅剩 144G，每 VM 一层 24.5G qcow2 的 COW overlay
2. **把 MCP 依赖烤进 qcow2 镜像** —— 省每任务 2.5 分钟，20 任务省 50 分钟，
   361 全集省 15 小时（M0 note §6 提过）

**全集时间估算**（idea §11 要求 361 任务 × Setting I 三轮）：
串行 ~16.5 天；4 路并行 ~4 天；再烤依赖 ~3.5 天。
