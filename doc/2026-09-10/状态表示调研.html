01

我们的问题，先说清楚

EvoTree 把「agent 现在处于什么局面」压缩成一个三元组，两个三元组相等就认为是同一个局面、树上的同一个点：

StateSig(app: str, window: str, dialog: Optional[str]) 例：("Gnome-control-center", "Settings", None)

三轮实验实测出三个毛病，而且方向相反：

  • 太粗——GNOME 系统菜单开着 / 关着，φ 完全相同。fe41f596 花了 8 步中的 2 步只为关掉一个挡住视线的菜单，树里看不见这件事
  • 太细——Nautilus 搜索框把 agent 自己输入的查询串带进了窗口标题（window='Search for "cp file1 dir1 dir2 dir3"'），换个查询就是新节点，树碎掉
  • 维度残缺——dialog 恒为 None，因为我们跑 --observation_type screenshot，从不采集 a11y 树

更根本的是双模态：我们的 agent 每步在 GUI 动作（pyautogui.click，无返回值）和 CLI/工具调用（os.open_shell，有返回值）之间二选一。 而 φ 只描述屏幕——终端任务里「已复制 0 个文件 → 已复制 3 个」这样的状态变化，φ 完全看不见。

02

核心答案：一半对，一半错

我一开始的判断是「几乎没人用离散状态键」。查完之后必须收回。 在双模态（GUI+工具）这个窄切面上确实没有；但只要放宽到 GUI agent， 离散状态图是个正在活跃的子领域，而且有几个做得比我们彻底得多。

「节点是离散状态而不是轨迹」不能当作新意来讲——DroidBot 2023 年就这么做了。

而且要注意这批工作的演进方向：DroidBot 用精确哈希 → EAM/UI-KOBE 改成「嵌入召回 + 模型验证」两段式。 他们从精确元组走开，正是因为元组既会过度合并、又会过度分裂——就是我们现在遇到的两个病。

真正还没人做的，是「跨任务持久图 + 边上同时挂成功率和 cost-to-go + 真实桌面环境」这个组合。 ScreenSearch 有边级统计但只做探索不管任务成败；EAM 有 Q 函数但在 Android；GATS 两样都有但只在合成环境跑过。

一个可以直接抄的数字

GiGPO 在 ALFWorld 上实测：超过 65% 的状态会在不同轨迹间重现。这是「状态复用值不值得做」的直接证据， 也给了我们一个该测的指标——我们的树里状态重现率是多少？如果远低于 65%，说明签名太细了。

SWE-agent 有一个几乎一样的状态元组

这是三路调研里最推翻我预期的一条。SWE-agent（解 GitHub issue 的 agent）每一步都往 /root/state.json 写一个二元组， 然后注入进每一次观测：

state["open_file"] 当前打开的文件 state["working_dir"] 当前工作目录 模板注入：(Open file: {{open_file}}) (Current directory: {{working_dir}})

这就是 φ，只是维度不同。而且细节上有两点值得抄：空值用 "n/a" 哨兵而不是 None； 每步用 state_commands 重算，不缓存。

关键差别，也是我们真正的错误

SWE-agent 是向环境「查询」状态，我们是从屏幕「解析」状态。

它执行一条 shell 命令拿到 pwd 和当前文件——精确、廉价、无歧义。 我们从窗口标题里正则匹配——于是 Nautilus 把搜索查询串塞进标题时，我们的状态就碎了。

而我们有 shell 权限（os.open_shell）。pwd、文件数、进程状态都是可以直接问出来的， 不必从像素里猜。

而且它测过「全历史 vs 重算状态」 SWE-agent Table 3 消融
Full history 15.0 Last 5 Obs. 18.0 ← 丢掉历史、每步重算状态，反而更好

这是文献里唯一一个直接比较「把历史当状态」和「重算状态」的数字，而且重算赢了 3 个点。

但工具返回值属于状态，这条是共识

ToolCUA 把它直接写进了 MDP 的形式化定义里（本地 ref/toolcua 有源码，与已发表版本一致）：

At each time step t, the state st ∈ S denotes a multimodal observation encompassing both the desktop screenshot and previously invoked tool results. The agent interacts with the environment through a hybrid action space A = AGUI ∪ ATool [已核实] arxiv.org/html/2605.12481 §2.1

注意这里的不对称：动作空间被拆成两个子空间，状态空间没有拆——一个 st 同时承载屏幕和工具历史。

按这个形式化，我们树里「工具边和 GUI 边挂在同一个 φ 节点上」是对的。错的是 φ 只覆盖了屏幕那一半。

唯一的量化证据，而且很弱 UltraCUA Table 6 消融

UltraCUA 用自然语言维护「进度」，作者说它对「跨动作模态切换」的场景很关键：

This mechanism proves crucial for multi-step tasks requiring information persistence across action modality switches. [已核实] arxiv.org/html/2510.17790 §2.3.2
开启 working memory 成功率 27.0% 平均 8.46 步 关闭 working memory 成功率 25.4% 平均 8.56 步

作者自己称这个增益 "modest"（不大）。这是我们能找到的关于「混合模态进度状态」的唯一量化数据，而且是自由文本形式，不是离散键。

一个反直觉的警告

ToolCUA 实测：粗暴地把两种动作空间都摆出来会让效果变差。Qwen3VL-235B 加了工具后，平均每条轨迹调用 6.10 次工具，准确率反而从 41.14% 掉到 38.14%。而它们训练出的最好模型平均只调用 0.74 次工具，准确率 46.8%。

少而准的工具调用胜过多而滥。这对我们的推荐栏有直接含义：推荐工具动作本身不是好事。

03

但我们的问题有人解过 —— 在另外两个领域

LASER：状态等价该按「结构」而不是「内容」

LASER 是把网页导航建模成状态空间探索的工作。它对「两个观测什么时候算同一个状态」给了一句极其干净的判据：

we consider an agent to be in two different states only if the structure of the current environment observation is different. This allows us to define only a handful of states to support an agent's exploration in a complex environment fully. [已核实] arxiv.org/html/2309.08172 §2.3

整个 WebShop 域只用了 4 个状态，每个状态配一套专属的可用动作集。

这条判据同时治我们两个方向相反的病：

  • Nautilus 搜索框换个查询串 → 结构没变（还是「搜索结果页」）→ 同一个状态 → 治「太细」
  • 菜单开着 / 关着 → 结构变了（多了一个浮层）→ 不同状态 → 治「太粗」

代价是论文自己承认的：状态要手工枚举，「might only be suitable for building agents for specific domains rather than open-world web agents」。

Android GUI 测试：APE 把我们三个毛病写在同一段里

这是本次调研最有价值的发现。APE 是一篇 Android 自动化测试的论文，它要给 app 建一个状态模型来指导探索——和我们建经验树是同一个工程问题。 它对「粗细两难」的描述，几乎是逐字命中我们的处境：

First, if the model is overly fine-grained, the testing tool cannot systematically explore the model due to state explosion. Second, if the model is overly coarse-grained, the testing tool cannot gather sufficiently accurate knowledge... an ineffective abstraction may map multiple GUI actions with different behaviors (e.g., leading to different target states) to the same model action. [已核实] rh_research_ape.txt §I

它举的例子就是我们的 Nautilus 问题：一个文件列表界面，把文件名放进状态签名会导致状态爆炸，不放进去又会把行为不同的动作合并成一个。

它给出的检测信号，我们的数据里已经有了

a state transition (S, α, S′) is non-deterministic if there is another transition (S, α, S″), where S′ ≠ S″. Such a pair of non-deterministic transitions usually indicates that the abstraction of the source state S or the model action α is overly coarse and needs to be refined. [已核实] rh_research_ape.txt §III
这条可以直接用

翻译成我们的话：同一个状态、同一个动作，有时成功有时失败 → 这个状态被合并得太粗了，该拆。

而这个信号我们已经在采集了——就是 p 落在 0 和 1 之间的那些边。不需要猜该加哪些维度，数据会告诉我们哪个节点该拆。

在我们 pass3 的树里跑一遍这个判据 22 条边，3 条命中
### Recursively_go_through_the_folders s0 --os.open_shell n=4 p=0.25 to_succ=s2 to_fail=s0 ← 非确定性 s0 --computer_use.key n=2 p=0.50 to_succ=s0 to_fail=s0 ← 非确定性 ### Copies_file__arg0__to_each_of_directories s0 --computer_use.type n=7 p=0.43 to_succ=s6 to_fail=s0 ← 非确定性

这三条边正是三轮实验里第一次出现的中间 p 值。当时我把它们当作「三轮成功拉开了 p 值」的好消息报给你—— 按 APE 的判据，它们同时也是「s0 这个节点被合并得太粗」的报警。 注意 s0 的签名是 (unknown, '', None)——三个字段全空的那个节点。

APE 的完整算法还包括防止拆过头的机制：如果一次细化让一个状态裂成超过 δ 个新状态（默认 8），就回退。 实测在 1316 个 app 上覆盖率相对提升 14–78%，发现 61 个独特崩溃（对照组 31–44 个）。

取值型工具调用该建模成「自环边」

这条正面回答了我们的双模态问题。ActionEngine 把两类操作分开处理：

UI Manipulation Operations typically induce a transition to a new state, whereas Data Collection Operations introduces self-loops because they do not change the agent's state in the graph. Instead of triggering a state transition, these operations extract information from the UI and store it in symbolic variables that can be referenced in the online execution stage. [已核实] arXiv 2602.20502 §3.1

对我们的直接含义：os.get_volume、os.get_text_scale 这类只读取不改变的工具调用， 不该被当成普通的状态转移边——它们是自环边，作用是往符号变量里绑值。

而 os.set_volume、os.copy_matching_files 这类会改变系统状态的调用才是真正的转移边。 我们现在把两者混在一起，所以「查了一下音量」和「改了音量」在树里长得一样。

Stoat 的归一化规则：2017 年就写好了我们要的那条

(2) minor UI information, e.g., text changes (e.g., the contents of TextViews/EditTexts) and UI property changes, is omitted without creating new states; (3) ListViews are only differentiated as empty and non-empty. [已核实] Stoat, FSE 2017

第 (2) 条就是我们的 Nautilus 修复——输入框里的内容不进状态签名。 第 (3) 条是处理变长列表的标准答案：把集合压成「空 / 非空」这样的有界类别，而不是去哈希内容。

这两条规则比我们的 normalize_window 正则简单得多，也稳健得多。

DroidBot：同时维护两个粒度的键

这是最直接可抄的工程做法。DroidBot 对每个界面同时算两个键：

self.state_str = 内容敏感 ← 含 text / enabled / checked / selected self.structure_str = 内容无关 ← 只含 class + resource_id

粗键把 Nautilus 所有搜索结果页塌成同一个节点（不管查询串是什么），细键在行为真的分叉时才用来区分。

还有一个观察值得注意：它的键是控件签名的有序集合。集合天然有序无关、天然去重，而且——弹窗只是多了几个控件，不需要单独的 dialog 字段。 按这个思路，我们那个死掉的第三维不是要「补上」，而是要取消。

一个反面教材

AutoDroid 在 DroidBot 基础上用一串正则做归一化。调研核实了它的实际代码，是有 bug 的：漏了个逗号让 'Dec' 'January' 拼成 'DecJanuary'；没加锚点的正则把 "Satisfied" 变成 "isfied"；含 : 或 % 的字符串直接被清空；而 '[0-9]+' 那条被注释掉了——他们试过全剥数字，然后退回来了。

这就是「不断加正则」这条路的终点。我们的 normalize_window 正走在同一条路上。

最反直觉的一条：像我们这样的系统，应该要更粗的状态

有一篇实证研究把网页语料固定住，只换状态抽象函数，看能产生多少个状态：

同一批页面，六种抽象函数： StrCmp 1756 个状态 ← 最细 RTED 268 PDiff 65 Judge 154 WebEmbed 10 Gestalt 18 ← 最粗 同样的页面，状态数差 近百倍，纯粹取决于抽象函数怎么选。

而它的核心结论，对我们是当头一棒：

Strict and fine-grained abstractions benefit model-based approaches, whereas compact abstractions enhance the stability of RL-based approaches. [已核实] arXiv 2606.16650 §5

原因它也讲了：细粒度状态会让每个状态拿不到足够的访问次数，Q 值更新不稳定， 基于 RL 的方法「degenerates toward nearly random exploration」——退化成近乎随机探索。

EvoTree 的边上挂着成功率和 cost-to-go，我们就是那个「价值学习」的消费者。 这意味着我们一直以来的直觉——「状态太粗了，要加维度」——可能是反的。

对照我们的实际数据：22 条边，n 最大才 13，一半以上的边 n≤2。我们的问题很可能不是状态不够细， 而是每个状态的样本本来就不够。再加维度只会让样本更稀。

这条改变了修复的方向

Li/Walsh/Littman 的实测也印证同一件事：出租车问题 500 个状态，用「保价值」的抽象只能压到 489 或 381， 用最激进的压到 6 个但破坏了最优性。安全的抽象几乎压不动，能大幅压缩的都不安全。

所以「给 φ 加第四、第五个维度」这个方向，很可能让事情更糟。

一个必须知道的坏消息：阈值会腐烂

ICSE 2020 有篇专门研究「状态抽象阈值」的工作，在 6000 多个网站、49.3 万个状态对上做了实测：

although RTED was able to achieve a high accuracy F1 score of 0.95 initially, the final produced model had only an F1 of 0.45. This deterioration is due to the accumulation of numerous near-duplicates. [已核实] Yandrapally, Stocco & Mesbah, ICSE 2020

一开始调得很准的抽象函数，随着状态积累会退化到几乎无用。 而且他们的形式化正好把我们的 φ 描述成了退化情况：抽象函数是一个 (距离度量, 阈值) 对， 我们的 φ 是「距离 = 元组不等、阈值 = 0、投影到 3 维」这个最简特例。

这条直接否掉了「一次性重新设计一个更好的 φ」这个思路。无论现在调得多准，树长大之后都会退化—— 除非抽象函数本身能随时间调整。

一个必须现在就定的架构决策

APE 之所以能重新抽象，是因为它保留了原始的界面树。

只存哈希的记忆树，日后永远无法重新抽象。我们现在存的是 StateSig 三元组，不是原始观测—— 这意味着如果将来要改抽象规则，已经积累的树只能全部作废重跑。这个决定要现在做，不是等森林长大之后。

强化学习理论：什么时候合并两个状态是安全的

RL 里「状态抽象」是个有几十年历史的题目，它给出的是判据而不是算法：

A Q*-irrelevance abstraction... for any action a, φ(s₁) = φ(s₂) implies Q*(s₁,a) = Q*(s₂,a) [已核实] Li, Walsh & Littman 2006 · rh_research_li06.txt §3.3

白话：只有当两个局面的「最优动作价值」相同时，把它们合并成一个状态才是安全的。

我们的菜单案例违反了这条——菜单开着时最优动作是「点空白处关掉它」，关着时是「往下滚」，两者的最优动作不同，合并就是错的。 而 Nautilus 案例是反方向的错：把最优价值相同的局面拆开了，白白损失数据效率。

这个判据的用法是当诊断工具：如果一个节点推荐出来的动作成功率呈双峰分布，说明这个节点混进了不同的局面。 老文献把这个现象叫 perceptual aliasing（知觉混叠）。

04

几个需要更正的既有认知

① Synapse 的「状态抽象」不是我们以为的那种

Synapse 有一个叫 "state abstraction" 的机制，名字听起来正是我们要找的先例。它不是。

To reduce the length of each state, Synapse takes advantage of the few-shot learning ability of LLMs to extract task-relevant information from raw states and form clean observations [已核实] arxiv.org/html/2306.07863 §3.2

它做的是token 缩减，产物是自由文本，从不被哈希或比对，没有等价关系。 更关键的是它按任务条件化——同一个屏幕在不同任务下抽象出不同结果，这和「规范化签名」的要求正好相反。 而且它的记忆键是未抽象的原始 HTML + 任务串，抽象只用在值那一侧。

② ToolCUA 不是 OSWorld-MCP 那批人做的

我先前说它是「同一批人的后续工作」——不准确。它是 Tongyi Lab（阿里）/ 复旦 / 上海 AI Lab，只是在 OSWorld-MCP 上做评测。写进相关工作时要改。

③ 「边比点更有信息量」有实验支持

Agent-S3 做过一个轨迹表示的对照实验（10 次 rollout）：

Screenshot Only 56.0 Trajectory Summary 55.0 Naive Captioning 56.8 Behavior Narratives 60.2 ← 逐「转移」提取事实
it is necessary to generate facts over transitions rather than individual states [已核实] arxiv.org/html/2510.02250 §4.4

这对我们是个正面信号：EvoTree 的边已经承载 p(e) 和 cost-to-go，重心本来就在边上。文献支持这个方向。

AutoManual 2405.16247 六类规则（含 Corrected Error、Unsolved Error），结果三分：直接成功 / 间接成功 / 失败 「出过错但后来解决了」这一类，正是我们边级信号该待的地方
Step-GUI 2512.15431 给失败的探索注入正确答案提示，转成「引导式成功样本」 需要训练，我们用不上

两条直接冲着我们边级统计来的警告

警告一：把整轮成败摊到每一步，实测会崩 ETO · ACL 2024 §4.4

ETO 对比了两种粒度，其中「步级」那种正是我们现在的记账方式——拿最终奖励标注每一步。

WebShop 平均奖励： SFT（不做对比） 63.1 轨迹级对比 67.4 步级对比 8.3 ← 完全崩溃 步级（调低学习率） 62.8 ← 仍低于不做对比
This instability may be attributed to the inaccurate estimation of the action quality, as we simply utilize the final rewards to construct step-wise contrastive pairs. [已核实] arXiv 2403.02502 §4.4

「用整轮成败给每条边打分」这个估计量本身有偏。我们能扛住的唯一理由是边被访问足够多次、误归因被平均掉—— 而我们 n 最大 13、一半以上 n≤2。推荐前应该设最小访问次数门槛，n 太小的边不该被当真。

警告二：75% 的失败是「点歪了」，不是「选错了」 OSWorld 官方错误分析 §5
Among the 550 failed examples, more than 75% exist mouse click inaccuracies, which is the most common error. The agent fails to click the correct coordinates despite planning detailed and accurate steps, indicating strong planning but weak execution. [已核实] arXiv 2404.07972 §5

一条标记为「失败」的边，四分之三的情况下动作本身是对的，只是没点准。 我们把两者混为一谈，结果是树在学着避开正确的动作。边上应该分开记 intent_failed（选错了）和 execution_failed（点歪了）。

配套解法：按观测标注边，别按自述

UI-Evol（OSWorld + Agent S2）的 Retrace：从截图差异反推实际发生了什么， 而不是采信 agent 声称做了什么——"free from noise introduced by invalid actions"。

这正好接上三轮报告里那个发现：agent 说「已执行」，但屏幕灰度三步纹丝未动。

AutoManual 给我们现在的设计起了个名字

它明确点出「只记成功」的失效模式：

Path Dependence（路径依赖）——"the agent blindly replicates the paths of previous successes, failing to adapt appropriately to new scenarios."

这正是我们三轮实验观察到的：系统只在它已经会做的任务上得到强化。

06

文献实际支持的几个选项

下面每一个都有出处。我不替你选，只把证据强度和代价摆出来。

A · 向环境查询状态，别从屏幕解析证据最强

照 SWE-agent 的做法：每步执行几条廉价命令取 pwd、当前应用、文件数，而不是从窗口标题正则匹配。空值用 "n/a" 哨兵。

为什么最强：这是文献里唯一一个和我们同构的状态元组，而且有消融数据（重算状态 18.0 > 全历史 15.0）。我们已经有 shell 权限，实现成本极低。

同时治三个病：太细（不再解析易变标题）、死维度（dialog 可以查）、工具进度不可见（files_copied=3/3 变成精确值）。代价：每步一次环境往返；把 φ 和操作系统细节耦合起来。

B · 状态等价按结构判定证据强

照 LASER：只有当观测的结构不同才算不同状态，内容变化不算。搜索框里换个查询串结构没变，菜单弹出来结构变了。

为什么强：一条规则同时治「太粗」和「太细」两个方向相反的病；LASER 用它把整个域压到 4 个状态。

代价：结构类别要手工枚举，论文自述只适合特定域。对我们意味着要为 os 域列一份「结构清单」。

C · 非确定性触发的自适应细化有现成信号

保留 φ，但从「固定元组」改成「运行时可细化」。同一状态同一动作导致不同结果时拆节点；拆过头（超 δ 个）回退。

为什么可行：APE 在 1316 个 app 上验证过，而且我们数据里已经有这个信号——22 条边中 3 条命中。

代价：细化后要重建子树，累积的 p(e) 和 cost-to-go 会失效——这一步要想清楚统计量怎么迁移。

D · 把工具进度加进状态证据中

状态改成「屏幕签名 + 工具结果摘要」，对应 ToolCUA 的 st。治「终端任务 φ 是废的」。

数据支撑：OSWorld-MCP 自述 42% 的任务需要多轮工具调用，最强模型纯 GUI 做四轮工具任务得分为 0——那正是屏幕-only φ 的盲区。

代价：UltraCUA 的自由文本版本只有 +1.6 个百分点，作者自称「modest」。而且很容易在新维度上重演「太细」——字节数会像查询串一样打碎状态。与 A 高度重叠，A 是它更精确的实现。

E · 重心从点移到边证据中

OS-Symphony 的循环检测能直接抓「8 步里 2 步在关菜单」，完全不需要更细的 φ。Agent-S3 的消融显示转移事实（60.2）优于状态表示（56.8）。

代价：削弱精确匹配查表；里程碑标注要每步一次 VLM 调用。但如果只在意「菜单浪费步数」这个具体病，这比重设计 φ 便宜得多。

F · 从失败里取信号方案完整

加 DOWNVOTE 式负面证据，采用 AutoManual 的三分结果（直接成功 / 间接成功 / 失败）。

AutoManual 给我们的病起了名：Path Dependence——"the agent blindly replicates the paths of previous successes"。

代价：失败轨迹内部的信用分配仍未解，AutoManual 用条件化提示缓解而非解决，误归因风险真实。

G · 双层键：粗键记统计，细键分歧时才用唯一同时治两病

照 DroidBot：每个状态同时算「内容无关」的粗键和「内容敏感」的细键。粗键上累积 p(e)，细键只在行为真的分叉时才用来区分兄弟节点。

为什么值得单列：这是所有选项里唯一一个同时解决「太粗」和「太细」的——其它选项都只能治一个方向。

代价：两套键要维护；必须决定统计量挂在哪一层。另外 DroidBot 的键是控件集合，按这个思路 dialog 维度应该取消而不是补上（弹窗只是多几个控件）。

H · 从转移记录里学动作等价今天就能做

AutoDroid 的规则：如果两个动作的（起点，终点）状态对相同，就合并它们。从我们已有的轨迹里就能算，不需要更好的观测。

它把动作空间从每状态 36.4 个选择压到 13.2 个。

代价：需要每条边有足够的重复遍历才可靠——我们现在 n 最大才 13；可能把「碰巧在已见轨迹上一致」的动作错误合并。
两条横跨所有选项的约束

① 别按模态拆树。UI-TARS-2 发现 GUI 和 SDK 共享一个价值模型比分开建更好，混合训练连纯 GUI 性能都提升了。

② 预期先降后升。ToolCUA 实测：光是把两种动作空间都摆出来就会掉分——Claude-4.5-Sonnet −13.5%，Qwen3VL 41.1%→38.1%（每轨迹 6.10 次工具调用）。它们自己的最优模型只用 0.74 次。少而准 > 多而滥，这对我们的推荐栏是直接警告：推荐工具动作本身不是好事。

08

我的判断（这部分是观点，不是文献）

你的直觉是对的。而且查完之后，我要收回自己一开始的判断。

我原本准备写的结论是「几乎没人做离散状态，我们在无人区」。这个结论是错的。 DroidBot 2023 年就在用 md5(activity + 控件签名集合) 当状态键，AutoDroid 拿它跑了 158 个任务， ActionEngine、EAM、UI-KOBE、ScreenSearch 都在建同样的图。方向没问题，问题在实现。

错误一：我们「解析」屏幕，而该「查询」环境。 SWE-agent 执行一条命令拿到 pwd 和当前文件——精确、廉价、无歧义。 我们从窗口标题正则匹配，于是 Nautilus 一把搜索串塞进标题，状态就碎了。 而我们有 shell 权限，这些本来都能直接问出来。

错误二：我们停在了这批工作的起点上。 注意先例的演进方向——DroidBot 用精确元组匹配，EAM 和 UI-KOBE 都改成了「嵌入召回 + 模型验证」两段式。 他们从精确元组走开，正是因为元组既会过度合并、又会过度分裂，就是我们现在这两个病。 我们等于在 2026 年重走了 2023 年的实现。

错误三，也是最反直觉的：我们一直想给 φ 加维度，方向可能是反的。 实证研究显示，像 EvoTree 这样在边上累积价值统计的系统需要更粗的状态——太细会让每个节点拿不到足够样本， 价值估计退化成噪声。我们 22 条边里 n 最大才 13，一半以上 n≤2。再加维度只会让样本更稀。

两条可以直接动手的具体结论：

  • dialog 维度不是「死了」，是「多余」。所有状态图系统都从屏幕内容推导身份， 而不是窗口外壳。DroidBot 的 activity{控件签名集合} 自动涵盖弹窗——弹窗只是多了几个控件。 把三元组的固定槽位换成「应用 + 窗口 + 显著元素的规范化集合」，「太粗」和「死维度」两个病一起消失。
  • 取值型工具调用该建成自环边。os.get_volume 这类只读不改的调用不改变状态， 应该是绑定符号变量的自环边；os.set_volume 这类才是真转移边。我们现在把两者混在一起。

还有一个架构决策要现在做：我们只存 StateSig 不存原始观测。 APE 能重新抽象是因为它保留了原始界面树，UI-KOBE 能事后审计合并是因为它留了参考截图。 而 ICSE 2020 那个 F1 从 0.95 掉到 0.45 的结果说明任何固定阈值都会随规模腐烂—— 也就是说我们迟早要改抽象规则。现在不留原始观测，到时候已积累的树只能全部作废。

关于定位：「节点是离散状态」不能再当新意讲了。真正还没人做的是 「跨任务持久图 + 边上同时挂成功率和 cost-to-go + 真实桌面环境」这个组合—— ScreenSearch 有边级统计但不管任务成败，EAM 有 Q 函数但在 Android，GATS 两样都有但只在合成环境跑过。 这个缺口是真的，但比我原以为的窄得多。

下一步我建议先做一次测量，不动设计。GiGPO 报告 ALFWorld 上超过 65% 的状态会跨轨迹重现—— 这给了我们一个该测的数：我们树里的状态重现率是多少？再加一个 APE 的检测： p 落在 0 和 1 之间的边，是不是集中在 (unknown, '', None) 那一个节点上？

另外两条与 φ 无关、但同样紧急的修正：

  • 推荐前设最小访问次数门槛。ETO 实测「用整轮成败标注每一步」这个估计量会崩（8.3 vs 67.4）。 我们靠「多次访问平均掉误归因」来扛，但 n 最大才 13——n 太小的边不该进推荐栏。
  • 把「选错了」和「点歪了」分开记。OSWorld 官方分析：75% 的失败是点击不准，动作本身是对的。 混在一起，树会学着避开正确的动作。

这两个数半天能出，而且能直接分诊：重现率低 → 签名太细，该走「查询而非解析」； 报警集中在空签名节点 → 根本不是设计问题，是那个节点压根没取到数据。 两种情况的修法完全不同，先测清楚再动手。
